## Public Content Rules

- Use verified resume and repository evidence. Do not invent metrics, users, responsibilities or project status.
- Treat the approved current resume as the content and layout baseline. Improve it incrementally; do not replace it with a parallel resume design without explicit approval.
- Use `philalimov.apps@gmail.com` on the portfolio contact page and retain `philalimov@gmail.com` on the approved resume. Do not publish a phone number, exact address or other private account details.
- Never copy personal adviser, health, relationship, financial, prompt-history or private input material into this repository.
- Keep employer content limited to public resume responsibilities and avoid proprietary implementation details.
- Use only first-party or generated visual assets that improve comprehension. Do not use product screenshots as decoration or add unlicensed stock assets.

## Implementation Rules

- Keep the site static with no publishing build step. Three.js 0.186.1 is locally bundled for the real 3D room; retain its MIT notice. Avoid additional runtime dependencies unless a clear requirement justifies them.
- Preserve relative paths for GitHub Pages and future custom-domain compatibility.
- Keep one `h1` per page, keyboard navigation, visible focus, reduced-motion support and a usable 390px layout.
- Do not introduce analytics, trackers, cookies or a third-party contact form without explicit approval and privacy review.
- Update `resume.html`, regenerate the PDF, and validate both whenever resume facts change.

## Validation

```powershell
npm test
npm run resume
npm test
```

For visual changes, run a local HTTP server and inspect `index.html` and `resume.html` at 390x844 and 1440x1000. Confirm no overflow, browser errors, inaccessible navigation or unintended extra PDF pages.

Studio changes need actual camera translation/rotation in the same geometric room,
constant FOV, prop pickup/put-down, and HTML alignment on real object planes.
Projects belong to the monitor, experience to a portrait notebook, the approved
resume to a desk folio, and contacts to the phone after an explicit screen tap.
Wall artwork is decoration. Do not restore dialogs, image swaps or a separate
side reader as the primary navigation experience.

Verify rapid interrupted navigation, hover/focus names, touch discovery, Escape
(including within the resume iframe), Back/Forward, reader scroll restoration,
Pause motion/system reduced motion and 320/390px portrait plus short landscape.
Keep the renderer on demand; no perpetual idle loop. Dragging the overview turns
the real camera. Handle module/WebGL/context failure by restoring ordinary HTML.
Texture failure must not remove room geometry or content. Do not claim procedural
models are photoreal or that headless checks prove real phone GPU performance.

Move canonical sections; never clone content with duplicate IDs or hide fallback
before initialization. Mounted sections use `scene-section-*` IDs and
`data-studio-section`; hidden anchors retain public fragment targets. Restore the
original IDs on fallback. Public hashes must not target visible mounted sections:
WebKit can re-anchor those on later layout/input and lose reader scroll. Arrow
keys must not hijack content or controls. Keep history scroll restoration manual
while the room is active and restore it when recovering the ordinary page.

Resume embeds the approved same-origin document in screen mode, retaining facts
and print layout. Frame navigation uses location replacement so it adds no joint
history step. Keep PDF, standalone and retry fallbacks. Regenerate only through
`scripts/render_resume.py` when resume content changes.

`npm run test:studio` uses development Playwright tooling (see README) and writes
ignored screenshots under `validation-artifacts/`. Inspect screenshots and
assertions. Runtime verification is local proof; deployment requires its own
authorization and production evidence. Older generated angle images remain as
comparison assets and are not used as navigation destinations.
